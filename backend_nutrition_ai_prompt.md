# Задача: AI-эндпоинты для распознавания еды по тексту и генерации меню

## Сервер
`http://144.31.189.154:8080` (NestJS + TypeORM + PostgreSQL, тот же backend что и в
`backend_fcm_payload_prompt.md` / `backend_pose_calibration_prompt.md`)

## Контекст

Сейчас клиент заносит еду в дневник питания только вручную: ищет блюдо в
справочнике `food_items` (`GET /api/nutrition/food?q=...`) и указывает граммовку.
Это медленно и требует, чтобы кто-то заранее завёл блюдо в справочник.

Нужно добавить AI-оценку по свободному тексту (клиент пишет "гречка с курицей
250г и чай с сахаром" → сервер сам оценивает состав и граммовку через Claude) и
AI-генерацию меню на день под целевые КБЖУ клиента.

В проекте уже есть работающий AI-функционал с точно таким же паттерном —
генерация программы тренировок: `POST /api/ai/generate-program` (только
возвращает результат, ничего не сохраняет) + `POST /api/ai/save-program`
(отдельный явный вызов, который уже пишет в БД после того как пользователь
посмотрел результат и подтвердил). Учёт токенов/лимитов там уже прикручен
(`operation` в истории usage: `generate_program`, `chat`, отдаётся через
`GET /api/ai/usage`). **Нужно сделать 4 новых эндпоинта по той же схеме**:
две "генерирующие" ручки, которые ничего не пишут в БД, и две "сохраняющие",
которые пишут — плюс завести для них новые значения `operation` в той же
таблице usage-истории (`parse_meal`, `log_meal`, `generate_meal_plan`,
`save_meal_plan` — либо только для 2 запросов к Claude: `parse_meal`,
`generate_meal_plan`, если `log-meal`/`save-meal-plan` не делают отдельного
вызова к Claude, см. ниже).

Существующие таблицы/связи, которые надо переиспользовать (ничего нового в
схеме не требуется — `food_items.category` уже есть как опциональное поле,
миграции не нужны):
- `nutrition_profiles` (клиент → пол/возраст/вес/рост/активность/цель).
  **Важно:** `bmr`/`tdee`/`targetCalories`/макросы **не хранятся** как поля
  профиля — они считаются на лету приватными методами `NutritionService`
  (`calculateBMR`/`calculateTDEE`/...) при каждом вызове
  `GET /api/nutrition/profile/:clientId` и возвращаются в отдельном блоке
  `calculations`. Для `generate-meal-plan` нужно переиспользовать именно этот
  расчёт (вызвать существующий `getProfile()`/вынести расчёт в public-метод),
  а **не** читать `targetCalories` из уже существующего `MealPlan` на эту
  дату — там значения снапшотятся один раз при создании плана и могут быть
  устаревшими относительно текущего профиля.
- meal-plan на дату клиента (`GET /api/nutrition/meal-plan/:clientId?date=...`)
  → meals (`type`: `breakfast`/`lunch`/`dinner`/`snack`, `time?`) →
  meal_items (`foodItemId`, `amountGrams`).
  Find-or-create meal-plan по `(clientId, date)` уже есть, но **инлайном
  внутри `NutritionService.getMealPlan`**, не как отдельный переиспользуемый
  метод — его нужно вынести (или продублировать) для `log-meal`/`save-meal-plan`.
  Find-or-create meal **по `type` внутри плана — не существует вообще**:
  `addMeal` сегодня безусловно создаёт новый `Meal`, в схеме нет
  `@@unique([mealPlanId, type])`, и на проде уже могут быть дубликаты meal
  одного `type` в одном плане. Эту upsert-по-типу логику нужно написать с
  нуля, и явно решить, как вести себя при уже существующих дублях (брать
  самый ранний/первый найденный по `type` — задокументировать это как
  best-effort поведение, раз уникальности на уровне БД нет).
- `food_items` (`name`, `caloriesPer100g`, `proteinPer100g`, `carbsPer100g`,
  `fatPer100g`, `category?`) — создаются через `POST /api/nutrition/food`.
  Case-insensitive поиск точного совпадения по `name` **для дедупликации при
  создании — не существует**: есть только `contains`+`insensitive` для
  поискового `GET /food?q=`, а `createFoodItem` вообще не проверяет дубликаты
  (полагается на `@@unique([name])`, который в Postgres регистрозависим —
  `"Гречка"` и `"гречка"` создадут два разных ряда). Нужно добавить
  `findFirst({ name: { equals, mode: 'insensitive' } })` перед `create`, и
  учитывать, что при параллельных запросах дедупликация всё равно не
  гарантирована (unique-констрейнт не спасает от разных регистров).

## 1. `POST /api/ai/parse-meal`

Оценивает состав и граммовку по свободному тексту. **Ничего не пишет в БД.**

### Тело запроса
```json
{ "text": "гречка с курицей 250г и чай с сахаром", "mealType": "lunch" }
```
- `text` — обязателен, произвольный текст на русском.
- `mealType` — необязателен (`breakfast`/`lunch`/`dinner`/`snack`), можно
  использовать как подсказку контекста в промпте (не обязательно).

### Ответ
```json
{
  "items": [
    {
      "name": "Гречка отварная",
      "amountGrams": 150,
      "caloriesPer100g": 110,
      "proteinPer100g": 4.2,
      "carbsPer100g": 21.3,
      "fatPer100g": 1.1
    },
    {
      "name": "Куриная грудка отварная",
      "amountGrams": 100,
      "caloriesPer100g": 165,
      "proteinPer100g": 31,
      "carbsPer100g": 0,
      "fatPer100g": 3.6
    }
  ],
  "usage": { "totalTokens": 412, "costUsd": 0.0021 }
}
```
- Каждая позиция текста → отдельный элемент `items` (Claude сам решает,
  сколько блюд в тексте).
- `amountGrams` — оценка веса порции: если в тексте есть явная граммовка —
  использовать её; если нет ("тарелка супа", "кусок торта", "горсть орехов")
  — оценить по типичным российским порциям.
- `caloriesPer100g`/`proteinPer100g`/`carbsPer100g`/`fatPer100g` — оценка
  пищевой ценности **на 100г** этого конкретного блюда (не общая калорийность
  порции — её потом считает клиент как обычно: `калории_на_100г * граммы/100`,
  так же, как уже работает с `food_items`).
- Промпт должен явно ориентироваться на **российскую кухню** и её типичные
  блюда/названия/способы приготовления (борщ, оливье, гречка, творог,
  куриная грудка на пару и т.п.), а не на усреднённые международные оценки.
- `usage` — токены/стоимость этого конкретного запроса, тот же формат, что
  уже отдаёт `generate-program` (для отображения в UI и учёта лимита).
- Лимиты/тариф — та же проверка, что и для `generate-program`: если у
  пользователя исчерпан месячный лимit токенов — ответ **403**, тело ошибки
  в том же формате, что уже используется (клиент уже умеет его обрабатывать).

## 2. `POST /api/ai/log-meal`

Сохраняет **уже подтверждённый пользователем** (возможно отредактированный
вручную после `parse-meal`) список позиций в дневник питания клиента.
**Не вызывает Claude** — чистая запись в БД по уже готовым данным.

### Тело запроса
```json
{
  "clientId": "uuid",
  "date": "2026-08-04",
  "mealType": "lunch",
  "time": "13:30",
  "items": [
    { "name": "Гречка отварная", "amountGrams": 150, "caloriesPer100g": 110, "proteinPer100g": 4.2, "carbsPer100g": 21.3, "fatPer100g": 1.1 }
  ]
}
```
`time` необязателен.

### Что делает (атомарно, в одной транзакции)
1. Найти (или создать, если ещё нет) meal-plan клиента на `date`. Переиспользовать
   логику из `NutritionService.getMealPlan`, вынеся её в отдельный метод —
   сейчас она инлайновая и не переиспользуется другими методами сервиса.
2. Найти meal этого meal-plan с `type == mealType`; если нет — создать новый
   meal (`time` если передан). **Такого upsert-метода в коде нет** — писать
   с нуля. Если у плана уже есть несколько meal одного `type` (текущий код
   это допускает), брать первый/самый ранний найденный, а не создавать ещё
   один.
3. Для каждого `item`: поискать в `food_items` запись с точным совпадением
   `name` без учёта регистра (`findFirst` с `mode: 'insensitive'` — такой
   дедупликации при создании сейчас нет, только в поиске `GET /food?q=`) —
   если нашлась, переиспользовать её id; если нет — создать новую запись в
   `food_items` с `category: 'ai'` (поле уже есть в схеме, миграция не
   нужна) — чисто для будущей аналитики "сколько продуктов создано AI".
4. Добавить meal_item (`foodItemId`, `amountGrams`) в meal из шага 2.

### Ответ
`{ "ok": true }` — клиент сам перезагружает дневник по существующему
`GET /api/nutrition/summary/:clientId`.

## 3. `POST /api/ai/generate-meal-plan`

Генерирует меню на день под целевые КБЖУ клиента. **Ничего не пишет в БД.**

### Тело запроса
```json
{ "clientId": "uuid", "preferences": "не ем рыбу, люблю острое" }
```
`preferences` необязателен, свободный текст.

### Что делает
1. Достаёт профиль питания клиента и уже посчитанные `targetCalories` +
   макросы (то же, что отдаёт `GET /api/nutrition/profile/:clientId` —
   переиспользовать существующий расчёт, не пересчитывать заново).
2. Просит Claude собрать меню на один день из **реалистичных российских
   блюд** (обычные продукты/блюда, которые едят в России — гречка, курица,
   творог, борщ, овсянка и т.п., НЕ усреднённая интернациональная еда),
   разложенное по `breakfast`/`lunch`/`dinner`/`snack`, так, чтобы сумма
   калорий/БЖУ по всем позициям укладывалась в целевые значения клиента с
   отклонением примерно ±5-10%.
3. Учитывает `preferences`, если передан (аллергии/непереносимости/вкусы —
   строго исключать то, что просит избегать).

### Ответ
```json
{
  "meals": [
    {
      "type": "breakfast",
      "time": "08:00",
      "items": [
        { "name": "Овсяная каша на молоке", "amountGrams": 250, "caloriesPer100g": 90, "proteinPer100g": 3.2, "carbsPer100g": 14, "fatPer100g": 2.5 }
      ]
    }
  ],
  "totals": { "calories": 2100, "protein": 140, "carbs": 210, "fat": 65 },
  "usage": { "totalTokens": 980, "costUsd": 0.0048 }
}
```
- `totals` — сумма по всем items всех meals (сервер считает и отдаёт, чтобы
  клиент не пересчитывал сам и мог сразу показать сравнение с целью).
- Лимиты/`usage` — то же, что в п.1.

## 4. `POST /api/ai/save-meal-plan`

Сохраняет **уже подтверждённое** (или отредактированное) меню целиком.
Не вызывает Claude.

### Тело запроса
```json
{
  "clientId": "uuid",
  "date": "2026-08-04",
  "meals": [
    {
      "type": "breakfast",
      "time": "08:00",
      "items": [
        { "name": "Овсяная каша на молоке", "amountGrams": 250, "caloriesPer100g": 90, "proteinPer100g": 3.2, "carbsPer100g": 14, "fatPer100g": 2.5 }
      ]
    }
  ]
}
```

### Что делает
То же самое, что `log-meal` (п.2), но для нескольких `meals` за один вызов,
в одной транзакции: найти/создать meal-plan на `date`, для каждого meal —
найти/создать meal нужного `type`, для каждого item — найти/создать
`food_item`, добавить meal_item.

### Ответ
`{ "ok": true }`.

## Важно

- `parse-meal` и `generate-meal-plan` — **только оценка**, ничего не пишут в
  БД. Запись происходит исключительно через `log-meal`/`save-meal-plan`,
  которые дергает клиент отдельным явным действием после того, как
  пользователь посмотрел/отредактировал результат. Это тот же принцип, что
  уже реализован в паре `generate-program` → `save-program` — не делать
  иначе.
- Ошибка превышения лимита токенов — **403**, в том же формате ответа, что
  уже отдают существующие AI-ручки (Flutter-клиент уже умеет его
  обрабатывать одинаково для всех AI-экранов).
- В промптах для `parse-meal` и `generate-meal-plan` явно закладывать
  российский контекст (блюда, продукты, названия, типичные размеры порций)
  — иначе модель по умолчанию скатывается в усреднённые
  интернациональные оценки.
- `caloriesPer100g`/`proteinPer100g`/`carbsPer100g`/`fatPer100g` в ответах —
  всегда **на 100г**, не на порцию — так же, как уже хранится в `food_items`,
  чтобы клиент мог использовать тот же код расчёта, что и для обычных
  продуктов из справочника.
- Сегодня `generate-program` парсит ответ Claude только через `JSON.parse` и
  бросает ошибку лишь при синтаксически невалидном JSON — структура
  (наличие нужных полей, что они числа) не проверяется вообще. Для
  `parse-meal`/`generate-meal-plan` это опаснее, чем для программы
  тренировок: цифры уходят напрямую в расчёт КБЖУ клиента. **Нужно добавить
  лёгкую валидацию структуры** ответа Claude (обязательные поля есть,
  `amountGrams`/`caloriesPer100g`/... — числа) перед тем как отдавать его
  клиенту, а не полагаться только на успешный `JSON.parse`.
- Для `operation` в usage-логе использовать **только 2 значения**:
  `parse_meal`, `generate_meal_plan`. `log-meal`/`save-meal-plan` не должны
  писать строку в usage-лог вообще — так же, как сегодня `save-program` не
  пишет туда ничего (usage-лог пишется один раз, только в момент вызова
  Claude, откуда и берутся реальные `input_tokens`/`output_tokens`).
  `AiUsageLog.operation` — обычная строковая колонка (Prisma `String`, без
  enum), так что новые значения не требуют миграции.
- 403 при исчерпанном лимите — это стандартный Nest `ForbiddenException`:
  тело `{ statusCode: 403, message: "...", error: "Forbidden" }`, без
  структурированного `code` и без числовых `usage`/`limit` полей в самой
  ошибке (эти цифры доступны только через `GET /api/ai/usage` или в success-
  ответе). Для новых ручек нужно бросать тот же класс исключения с
  аналогичным по стилю текстом, а не придумывать новый формат ответа.

## Как проверить

1. `POST /api/ai/parse-meal` с `{"text": "два яйца и тост с маслом"}` —
   должен вернуть 2-3 позиции с разумными граммовками и КБЖУ на 100г, без
   записи в БД (повторный вызов `GET /api/nutrition/summary/:clientId` не
   должен показать новых приёмов пищи).
2. `POST /api/ai/log-meal` с результатом из п.1 (или вручную собранным
   телом) — должен появиться новый приём пищи (или пополниться существующий
   того же типа) в `GET /api/nutrition/summary/:clientId` на нужную дату, с
   новыми/переиспользованными записями в `food_items`.
3. `POST /api/ai/generate-meal-plan` для клиента с уже заполненным профилем
   питания — сумма `totals.calories` должна быть близка к
   `targetCalories` профиля (±5-10%), блюда — узнаваемо российские.
4. `POST /api/ai/save-meal-plan` с результатом из п.3 — все `meals`/`items`
   должны появиться в дневнике на указанную дату разом.
5. Отправить запросы под пользователем, у которого исчерпан лимит токенов
   (или временно занизить лимит) — `parse-meal`/`generate-meal-plan` должны
   вернуть 403 в том же формате, что и `generate-program` при исчерпанном
   лимите.

## Затронутые эндпоинты/файлы (предположительно, нужно найти в коде backend)

- Стек — **Prisma**, не TypeORM: модели описаны в `prisma/schema.prisma`,
  доступ к БД — через `PrismaService`, инжектированный напрямую в плоские
  `*.service.ts` (`AiService`, `NutritionService`); отдельных
  repository-классов нет ни в `ai`, ни в `nutrition`.
- Модуль/контроллер `ai` (`src/ai/ai.controller.ts`, там же, где уже лежат
  `generate-program`, `save-program`, `usage`) — добавить 4 новых роута.
  Клиент к Claude — `AiGateway` (`src/ai/ai.gateway.ts`,
  `@anthropic-ai/sdk`, модель `claude-haiku-4-5-20251001` хардкодом,
  `max_tokens: 2048`, `temperature` не задаётся) — переиспользовать его же,
  не заводить отдельный клиент.
- Сервис учёта токенов/лимитов (`AiService`, лимиты по `TrainerSettings.plan`
  через `PLAN_TOKEN_LIMITS`, `AiUsageLog` — сумма `totalTokens` с начала
  месяца) — переиспользовать логику проверки лимита для новых `operation`
  типов; миграция не нужна, `operation` — просто строка.
- Модуль/сервис `nutrition` (`src/nutrition/nutrition.service.ts`, там же,
  где `meal-plan`, `meals`, `food`) — **не всё из описанного выше
  переиспользуется напрямую**:
  - find-or-create meal-plan по дате — есть, но инлайном в `getMealPlan`,
    нужно вынести в переиспользуемый метод;
  - find-or-create meal по `type` — нужно написать с нуля (см. раздел про
    `log-meal` выше);
  - case-insensitive find-or-create `food_items` по `name` — нужно написать
    с нуля (сейчас `mode: 'insensitive'` используется только в поиске
    `GET /food?q=`, не при создании).
